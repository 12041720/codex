## 助手

已接续当前课程。三题均抓住了正确边界，但第 2 题需要补充一层精度。

1. **正确。**模型只能提出 `read_file` 调用；如果 Registry 没有对应执行器，Runtime 不能凭模型输出创造执行能力，文件不会因此被读取。

2. **方向正确。**本题给出的 `{"cmd":` 不是完整 JSON，首先在参数解析层失败，还没有进入业务参数校验、授权或执行。以后要严格区分三种情况：非法 JSON 是语法解析失败；合法 JSON 但缺少 `cmd` 等必填字段，是结构/语义校验失败；参数都合法但目标不允许，是授权/隔离拒绝。

3. **正确。**格式正确只说明数据能被解析，不能替代授权。执行前的策略、审批或隔离后端仍必须判断目标是否允许；不允许的路径不能因为 JSON 合法就执行。具体由哪一层先拒绝，要以当前工具的真实调用链为准。

因此，第二课练习记为**通过**，但不是把三题当作已经掌握整个工具系统。当前证据只覆盖简单场景下的 Spec/Executor 区分、Registry 查找、参数解析和授权边界。

## 难度调整

后续不再只问“能不能执行”这种单点判断，而会给出带有时间顺序和故障窗口的场景，要求同时回答：

1. **源码追踪题：**给出一个带 `call_id` 的 Function Call，从 `handle_output_item_done` 开始，指出 `ToolCallRuntime`、`ToolRouter`、`ToolRegistry` 和具体 Executor 各自接收、增加或改变了哪些信息；哪些结论必须回到源码，不能凭模块名称猜。
2. **故障分析题：**参数已解析、进程已经写入文件，但工具 Future 尚未返回，用户此时取消 Turn。分别判断“副作用已发生”“Tool Result 已产生”“结果已写入 history”“rollout 已持久化”“是否可以安全重试”这五件事能否独立成立，并说明需要哪些证据。
3. **系统设计题：**设计一个至少一次执行语义下的写文件工具恢复方案：定义持久状态、操作标识、重启后的判定分支和幂等策略；再说明为什么对带外部副作用的操作不能只靠 `call_id` 宣称 exactly-once。

下一课仍从 `ToolInvocation` 开始，但会直接使用这类调用链和部分成功场景验收，不提前宣布已经掌握恢复或并发。
